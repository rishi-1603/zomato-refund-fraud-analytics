# Methodology & Validation
### How the refund-fraud risk pipeline was built — and how we know what it achieves

---

## 1. Pipeline
```
data/raw/Zomato Dataset.csv        (45,584 real delivery orders — public Kaggle data)
        ↓  notebooks/01 (seed=42, fully reproducible)
+ Customer_ID (10,000 synthetic customers)
+ Refund_Requested / Refund_Reason / Refund_Amount   (synthetic layer, planted risk)
        ↓  data/processed/zomato_with_refunds.csv
        ↓  notebooks/02 — EDA   notebooks/03 — risk scoring
        ↓  scripts/validate_risk_score.py — score vs planted ground truth
        ↓  sql/fraud_queries.sql (PostgreSQL) · dashboard/app.py (Streamlit) · .pbix (Power BI)
```

## 2. Data provenance — the most important honesty point
- **Real:** delivery/logistics columns (delivery person, weather, traffic,
  timings, city, order type) — public Zomato dataset, unmodified.
- **Synthetic:** `Customer_ID` and all refund columns, generated by a seeded
  notebook. The generator *assigns* each customer a planted risk category
  (3% High / 7% Medium / 90% Low) and generates behaviour from it:
  High → 70% refund probability with repetitive reasons; Medium → 20%; Low → 5%.
- **Consequence:** every "fraud pattern" found (reason repetition, refund
  concentration) is planted by construction. The project demonstrates the
  *method*; the patterns are not discoveries about real Zomato users.

## 3. Risk score (full formula: `docs/risk_scoring_methodology.md`)
Eligibility: ≥5 orders AND refund rate >30% (279 customers) →
signals (refund rate 40%, reason repetition 30%, refunds/day 20%, reason
length 10%), min-max scaled → composite 0–100 → tiers Low ≤40 < Medium ≤70 < High.

## 4. How this is validated (the trust layer)
| Check | Where |
|---|---|
| Dataset integrity: row counts, uniqueness, refund-flag/amount consistency, reason validity, raw-data immutability | `tests/test_data_quality.py` |
| Suspects CSV reproduces exactly from the orders data (no hand-edited numbers) | `tests/test_risk_pipeline.py` |
| Tier thresholds match documentation | same |
| Ground-truth recovery is 100% reproducible (seeded) | same |
| Headline metrics (100% precision, low recall) hold on every run | same |
| Known raw-data quirk (53 ratings of 6.0) pinned, not hidden | data-quality tests |
| Score validation vs planted labels | `scripts/validate_risk_score.py` → `reports/score_validation.md` |

17 automated tests, all green in CI.

## 5. Reproducibility
```bash
pip install -r requirements.txt
streamlit run dashboard/app.py            # the dashboard
python scripts/validate_risk_score.py     # regenerate validation report + labels
python -m pytest tests/ -v                # all 17 checks
```
The refund layer can be regenerated end-to-end from the raw dataset with
`notebooks/01` (seed 42) and reproduces the committed data bit-for-bit on the
Customer_ID and Refund_Requested columns.

## 6. SQL layer
`sql/fraud_queries.sql` — 8 business queries (refund summary, top suspects,
reason repetition, reason distribution, amount analysis, city comparison,
high-risk identification, KPI report) for the PostgreSQL table created by
`notebooks/04_load_to_postgres.ipynb`. Each query is labelled with the
business question it answers.
